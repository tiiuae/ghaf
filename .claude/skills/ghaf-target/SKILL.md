# Ghaf target contract

A Ghaf device is not one machine. It is a host plus a fleet of microVMs on an internal
network, and almost every mistake in this workflow comes from talking to the wrong one or
calling it by the wrong name. This skill is the shared map; the other `ghaf-*` skills
assume it.

## Where the device details come from

`.github/skills/ghaf-hw-test/config.yaml` is the single source of truth, keyed by physical
machine (`darter-pro`, `Lenovo-X1`, `dell-7330`, `NUC`, `Orin-AGX`, `Orin-NX`). Read it
rather than asking the user for things it already knows:

```bash
nix-shell .github/skills/ghaf-hw-test/shell.nix --run \
  'python3 -c "import yaml;print(yaml.safe_load(open(\".github/skills/ghaf-hw-test/config.yaml\"))[\"devices\"][\"darter-pro\"])"'
```

Fields that matter here: `host_ip` (the device's reachable address), `usb_iface` (the
host-side NIC facing it, typically `ghaf-usb`), `serial_device` / `serial_baud`,
`flash_drive`, `ghaf_target`, `test_device_name`.

Per-machine values — `host_ip`, `ssh_identity`, `netboot_iface`, `netboot_mac`, `flash_drive`,
`serial_device` — live in the gitignored `config.local.yaml` beside it, merged over the shared
file per field. `config.yaml` deliberately leaves them null, because they describe a particular
desk rather than the project. `config.local.yaml.example` shows the shape.

If `host_ip` is null in both, ask the user for the address once and offer to write it into
**`config.local.yaml`** — guessing an address on a lab network can land you on someone else's
device, and writing it to the shared file leaks lab topology into the repo.

Note `ssh_identity`: when a device is reached by a key ssh would not offer by default, every
command fails with "Permission denied (publickey)", which reads like the device being down
rather than a missing key.

## The address map

Verified against a built system's `/etc/hosts`. The internal network is `192.168.100.0/24`
and every VM resolves by name from any VM on it:

| Name | Address | Notes |
|---|---|---|
| net-vm | 192.168.100.1 | owns the physical NIC — this is what you reach from outside |
| ghaf-host | 192.168.100.2 | the hypervisor host; where `microvm@*.service` units live |
| audio-vm | 192.168.100.3 | |
| gui-vm | 192.168.100.4 | desktop, greetd, login |
| admin-vm | 192.168.100.5 | givc admin, and the journal collector when logging is on |
| business-vm | 192.168.100.101 | appvms start at .101 |
| chrome-vm | 192.168.100.102 | |
| comms-vm | 192.168.100.103 | |
| flatpak-vm | 192.168.100.104 | |
| media-vm | 192.168.100.105 | |

Generated by `modules/common/networking/hosts.nix`; appvms vary per profile, so treat the
.10x rows as typical rather than fixed. To see the real list for an image, read
`/etc/hosts` inside the built system closure, or run `ghaf-logs`' collector, which
enumerates whatever is actually there.

## Reaching things

The device's external address belongs to **net-vm**, because it holds the passed-through
NIC. Everything else is one hop further in:

```bash
ssh ghaf@<host_ip>                          # lands on the device (net-vm side)
ssh ghaf@<host_ip> -- ssh ghaf-host          # the hypervisor host
ssh ghaf@<host_ip> -- ssh gui-vm journalctl -b --no-pager   # a specific VM
```

For `nixos-rebuild` the same topology is expressed as ssh config, documented in
`packages/pkgs-by-name/ghaf-build-helper/package.nix`:

```
host ghaf-netvm   user root   hostname <target-ip>
host ghaf-host    user root   hostname 192.168.100.2   proxyjump ghaf-netvm
```

Which hop you need depends on the question. Host-level things — microvm units, PCI
passthrough, the hypervisor journal — live on `ghaf-host`. Anything about the desktop,
login, or an application lives in its VM.

## Two names for the same machine

Keep these apart; conflating them produces failures that look like something else:

- **What you build and flash** is now generic. x86 laptops share `intel-laptop-debug`;
  `modules/reference/hardware/intel-laptop/` passes display, network and audio through by
  PCI *class wildcard* rather than per-device IDs, so one image serves the fleet.
  Per-machine targets still exist but are no longer the default path.
- **What the test suite is told** is machine-specific. `robot-test -d` accepts only
  `darter-pro`, `lenovo-x1`, `dell-7330`, `x1-sec-boot`, `orin-agx`, `orin-agx-64`,
  `orin-nx`. `Robot-Framework/config/variables.robot` compares `DEVICE_TYPE` against those
  exact lowercase strings to set `IS_LAPTOP`, so a wrong value doesn't error — it quietly
  runs the wrong subset of tests.

Jetson targets must be named as `-from-x86_64` variants from an x86 build host; the native
aarch64 attribute names are not exposed in `packages.x86_64-linux` and resolve to nothing.

## Identifying what is actually running

Before trusting any conclusion about a device, confirm what is on it. A surprising amount
of debugging time goes to reasoning about code that was never deployed:

```bash
ssh ghaf@<host_ip> -- ssh ghaf-host readlink /run/current-system
ssh ghaf@<host_ip> -- ssh gui-vm readlink /run/current-system
```

If that store path exists in your local store, you can read the *exact* configuration that
is running — `/nix/store/<hash>-nixos-system-gui-vm-*/etc/` holds the generated
`pam.d/`, `systemd/`, `hosts` and so on. Reading the real artifact beats re-deriving what
you think the Nix evaluated to.
