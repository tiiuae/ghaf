# x86 secure A/B testing

The Intel development canary is additive; normal laptop targets are unchanged.
See the [shared architecture](/ghaf/dev/architecture/ab-update) for trust,
signing, transactions and acceptance rules.

| Artifact | Target |
| --- | --- |
| Initial unsigned disk | `intel-laptop-debug-secure-ab` |
| Update payload | `intel-laptop-debug-secure-ab-sysupdate` |
| Installer ISO/environment | `intel-laptop-debug-installer` |

The initial build creates GPT, a Type-2-only ESP, active and empty root/verity
pairs, Btrfs persist and swap in plain LVM using stock tools inside a disposable
Nix build VM. LUKS2 is created on the device during first boot. The build host requires KVM; its storage devices are not used. EFI signing is separate so keys stay outside the
store. Each root is 50 GiB and each verity LV 1 GiB; with 12 GiB swap and 2 GiB
persist the default disk needs approximately 121 GiB. Smaller images reject.

## Execution locations and handoffs

Use this PR's Ghaf checkout on the x86 build host. Run its commands from the
checkout root in Bash, with Nix, `jq`, Python 3, coreutils and util-linux
available. Enter `nix develop` in that checkout first to obtain its `jq` and
Python tools. Record `git rev-parse HEAD` and the GIVC pin from `flake.lock`.
The installer USB, payload-data medium and installation destination are three
distinct devices in this procedure. Obtain their paths from `lsblk` and match
model/serial numbers before writing or mounting them.

| Step / machine | Input produced by | Output used next |
| --- | --- | --- |
| Key generation / build host | One-time local key generator below | `$GHAF_DEV_KEY_DIR`, retained for all builds/signing |
| Initial build / build host | Keys → public config export for generation 1 | `result-x86-unsigned` Nix-store directory |
| Initial signing / build host | Unsigned disk plus the same local keys | `/var/tmp/ghaf-x86-signed`, copied to data medium |
| Installer build / build host | Ordinary installer target from the same checkout | `result-x86-installer/iso/*.iso`, written to installer USB |
| Install / booted installer | Mounted signed-image directory and selected destination disk | Written SSD and enrolled firmware trust |
| First boot / laptop | Installed SSD | Device-encrypted storage, recovery credential if enrolled, accepted generation |
| Update build/sign / build host | Same keys and a newer generation from host baseline | `$SIGNED_DIR` and `$SIGNED_MANIFEST`, sent through HTTP delivery |
| Fetch / `net-vm` | HTTP origin and generation printed by build host | Shared host manifest path printed after successful fetch |
| Stage/reboot / Ghaf host | Printed manifest path plus built-in trust files | New healthy generation or fallback; compare baseline/sentinel |

Each shell has its own variables. Re-enter values at the explicit prompts after
changing machines; do not reuse a build-host path in the installer or a VM.

## Build and sign

**Build host.** Start with generation 1 only for a fresh device. This creates
keys if the chosen directory does not exist; reuse existing keys for a device
already enrolled with them. The exporter copies only public trust into a fresh
directory. Keep that directory unchanged after building.

```bash
set -euo pipefail
export GHAF_DEV_KEY_DIR="$HOME/.local/share/ghaf-dev-keys"
if [ ! -d "$GHAF_DEV_KEY_DIR" ]; then
  nix run .#ghaf-dev-keygen -- --output "$GHAF_DEV_KEY_DIR"
fi
GENERATION=1
PUBLIC="/var/tmp/secure-ab-x86-generation-$GENERATION"
nix run .#ghaf-secure-ab-config -- --key-dir "$GHAF_DEV_KEY_DIR" \
  --generation "$GENERATION" --output "$PUBLIC"
timeout 2h nix build --override-input secure-ab-build-config "path:$PUBLIC" \
  .#intel-laptop-debug-secure-ab -o result-x86-unsigned
SIGNED_IMAGE_DIR=/var/tmp/ghaf-x86-signed
TMPDIR=/var/tmp nix run .#ghaf-sign-x86-image -- --key-dir "$GHAF_DEV_KEY_DIR" \
  --input result-x86-unsigned --output "$SIGNED_IMAGE_DIR"
```

Outputs on the build host: `$PUBLIC` contains `config.json`, `PK.crt`,
`KEK.crt`, `db.crt` and `update.pub`; `result-x86-unsigned` points to the Nix-store
disk directory; `$SIGNED_IMAGE_DIR` is a separate signed directory. The signer
requires a new output directory and writes the image, bmap, `.auth` enrollment
files, `db.crt` and `public-trust.json`. The next section transfers that complete
signed directory. Private keys stay under `$GHAF_DEV_KEY_DIR`.

Signing expands the approximately 121 GiB raw image into `$TMPDIR`, then
recompresses it. Use a disk-backed temporary directory with room for the full
raw image plus the signed compressed output; a small `/tmp` tmpfs is unsuitable.
The temporary raw image is removed when the signer exits.

The signing input must be the trusted, immutable Nix build output, including
its `esp.sha256` inventory. Do not use a mutable copy: replacing both the image
and its inventory would bypass the integrity check.
The post-build signer edits the ESP with offline FAT tools as an ordinary user.
Before signing, it verifies the complete ESP file list and hashes against the
build inventory, rejecting changed, missing or additional files.
It checks all four public
trust files against the evaluation inventory, signs both systemd-boot paths and
every UKI, rejects Type-1 entries and regenerates the bmap in a new directory.

## Install and enroll

The secure A/B target above produces a disk image, not an installer ISO; there
is no `intel-laptop-debug-secure-ab-installer` target. Use the ordinary laptop
installer from this same checkout as the bootable environment containing
`ghaf-installer`:

```bash
nix build .#intel-laptop-debug-installer -o result-x86-installer
isos=(result-x86-installer/iso/*.iso)
test "${#isos[@]}" -eq 1 && test -f "${isos[0]}"
INSTALLER_ISO="${isos[0]}"
```

**Still on the build host**, identify the installer USB and an already formatted
payload-data partition using `lsblk`. The payload filesystem must support files
larger than 4 GiB, such as ext4 or exFAT. Copy the signed directory to its root,
then unmount it for transfer to the laptop:

```bash
lsblk -o PATH,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINTS
read -r -p 'Payload-data partition path (not the destination SSD): ' PAYLOAD_PARTITION
sudo mkdir -p /mnt/ghaf-ab-payload
sudo mount "$PAYLOAD_PARTITION" /mnt/ghaf-ab-payload
sudo test ! -e /mnt/ghaf-ab-payload/ghaf-x86-signed
sudo cp -r "$SIGNED_IMAGE_DIR" /mnt/ghaf-ab-payload/ghaf-x86-signed
sudo sync -f /mnt/ghaf-ab-payload
sudo umount /mnt/ghaf-ab-payload
```

Now select the separate installer USB **whole disk**, unmount its mounted
partitions shown by `lsblk`, and write the ISO. This destroys that USB's contents:

```bash
read -r -p 'Installer USB whole-disk path: ' INSTALLER_USB_DISK
test "$(sudo blockdev --getsize64 "$INSTALLER_USB_DISK")" -ge "$(stat -c %s "$INSTALLER_ISO")"
sudo dd if="$INSTALLER_ISO" of="$INSTALLER_USB_DISK" bs=4M status=progress conv=fsync
```

Outputs: a bootable installer USB and a separate payload medium containing
`ghaf-x86-signed/`. Move both to the laptop, enter UEFI Setup Mode, and boot the
installer USB. Its bundled ordinary laptop image is not the signed A/B image;
use the explicit `IMG_PATH` below rather than the TUI's default image.

**Inside the booted installer**, switch to a shell, for example with Ctrl+Alt+F2.
Device names may have changed; re-identify the payload partition by its serial
and filesystem. The build-host `/var/tmp` directory and shell variables are not
present here. Mount the transferred medium read-only and check all inputs:

```bash
set -euo pipefail
sudo systemctl stop ghaf-installer-tui.service
lsblk -o PATH,SIZE,MODEL,SERIAL,FSTYPE,LABEL,MOUNTPOINTS
read -r -p 'Payload-data partition path on this laptop: ' PAYLOAD_PARTITION
sudo mkdir -p /mnt/payload
sudo mount -o ro "$PAYLOAD_PARTITION" /mnt/payload
SIGNED_IMAGE_DIR=/mnt/payload/ghaf-x86-signed
test -d /sys/firmware/efi/efivars
for file in ghaf-image.raw.zst ghaf-image.bmap PK.auth KEK.auth db.auth db.crt; do
  sudo test -s "$SIGNED_IMAGE_DIR/$file"
done
```

Explicitly identify and authorize the destination disk before this destructive
step and set `INSTALL_DISK` to its exact path. It must be distinct from both
the installer USB and the data medium. Run inside the booted installer:

```bash
read -r -p 'Installation destination whole-disk path: ' INSTALL_DISK
sudo env IMG_PATH="$SIGNED_IMAGE_DIR" \
  GHAF_SECUREBOOT_KEY_DIR="$SIGNED_IMAGE_DIR" \
  ghaf-installer -s -d "$INSTALL_DISK"
```

Output: the destination disk contains the signed A/B image and firmware has
received the matching public trust. After installation, remove the installer
USB, boot the destination disk, and allow first-boot encryption and its reboot
to finish. Save any displayed recovery credential at that point; it is not in
the original signed bundle. Complete user provisioning, then inspect the host
baseline below.

The image contains plain LVM and the deferred-encryption marker; adding `-e`
is unnecessary. Before firmware changes the installer
checks the written ESP read-only, rejects Type-1 entries and verifies all loaders
and UKIs against `db.crt`. First boot encrypts in place with a fresh per-device
volume key through the existing deferred-encryption flow, then attempts hardware and recovery enrollment. Confirm the actual tokens and
recovery credential before treating enrollment as successful. Release uses an interactive, nonempty passphrase;
debug uses the known development passphrase `ghaf`. The current flow retains
the password slot even after hardware enrollment; debug images are not suitable
for protecting sensitive data. No empty bootstrap
LUKS keyslot is distributed in the image.

## Baseline after first boot

**Ghaf host after first boot.** Use its serial console, or obtain `net-vm`'s
external IP from the lab DHCP/router lease matched to the device's Ethernet MAC
and connect through it using the [SSH guide](/ghaf/dev/ref/ssh#connect). A direct
SSH connection to that external IP opens `net-vm`, not the host. Check `hostname`
and open a root host shell before running the following commands:

```bash
sudo -i
hostname
cat /proc/cmdline
cat /persist/common/ota/accepted-generation
ota-update image status
bootctl status --no-pager
bootctl list --no-pager
cryptsetup status crypted
veritysetup status nix-store
findmnt --mountpoint /nix/store
findmnt --mountpoint /persist
lvs -o lv_name,lv_size,lv_uuid pool
systemctl --failed
systemctl show ghaf-boot-health.service -p Result -p ExecMainStatus
journalctl -b -u ghaf-boot-health.service --no-pager
```

Expect matching running/accepted generations, an uncounted healthy default,
active LUKS and verity mappings, and no failed host units. Boot health is a
oneshot service: successful completion normally leaves it **inactive**, with
`Result=success` and `ExecMainStatus=0`. Its gate checks configured core VMM
services, not guest applications or login readiness.

Output to retain on the build host: the displayed accepted generation, selected
entry and slot/persist UUIDs, plus the sentinel digest below. Copy these values
out of the target session before rebooting; `/run` is not persistent.

Record the device model, SSD serial, Ghaf/GIVC revisions, Secure Boot state,
slot UUIDs and accepted generation. Resolve the encrypted partition with
`cryptsetup status crypted`; do not assume it is `/dev/sda3`. Inspect its
`cryptsetup luksDump` output for the expected hardware/recovery tokens and no
unfinished reencryption. Save recovery credentials separately from test logs.

Create a persistence sentinel once and record its digest outside the target:

```bash
install -d -m 0700 /persist/common/ota-test
printf 'A/B persistence test\n' > /persist/common/ota-test/sentinel
sha256sum /persist/common/ota-test/sentinel
```

## Build, deliver and install an update

**Back on the build host, in the same Ghaf checkout.** Enter a generation
strictly greater than the accepted value recorded from the host baseline. After
an initial generation 1, use healthy 2 then healthy 3 for A→B→A; use 4 for the
unhealthy test. For a device already updated, choose unused larger numbers.
Re-select the original key directory if using a new shell; do not regenerate it.
Use a fresh public directory and signing output for every candidate:

```bash
set -euo pipefail
export GHAF_DEV_KEY_DIR="$HOME/.local/share/ghaf-dev-keys"
read -r -p 'New generation, greater than the host baseline: ' GENERATION
PUBLIC="/var/tmp/secure-ab-x86-generation-$GENERATION"
SIGNED_DIR="/var/tmp/ghaf-x86-update-$GENERATION"
nix run .#ghaf-secure-ab-config -- --key-dir "$GHAF_DEV_KEY_DIR" \
  --generation "$GENERATION" --output "$PUBLIC"
nix build --override-input secure-ab-build-config "path:$PUBLIC" \
  .#intel-laptop-debug-secure-ab-sysupdate -o result-x86-update
manifests=(result-x86-update/*.manifest)
test "${#manifests[@]}" -eq 1 && test -f "${manifests[0]}"
MANIFEST="${manifests[0]}"
jq -e --argjson generation "$GENERATION" \
  '.target == "intel-laptop-debug-secure-ab" and .generation == $generation' "$MANIFEST"
nix run .#ghaf-sign-update -- --key-dir "$GHAF_DEV_KEY_DIR" \
  --input "$MANIFEST" --output "$SIGNED_DIR"
SIGNED_MANIFEST="$SIGNED_DIR/$(basename "$MANIFEST")"
```

Outputs on the build host: `result-x86-update` points to the unsigned payload;
`$SIGNED_DIR` contains the signed five-file bundle; `$SIGNED_MANIFEST` names its
signed manifest. Continue in this build-host shell with the
[shared HTTP delivery instructions](/ghaf/dev/architecture/ab-update#static-http-lab-delivery),
then fetch in a separate `net-vm` shell. Copy the resulting **host manifest**
path printed after successful fetch.

**Ghaf host, new root Bash shell.** The payload is already visible through the
shared `/persist/sysupdate` path. Enter the printed path, not the build-host
`$SIGNED_MANIFEST`. The public trust files below came from the installed image;
they are not downloaded from the HTTP server:

```bash
sudo -i
set -euo pipefail
hostname
read -r -p 'Host manifest path printed after fetch: ' MANIFEST
test -s "$MANIFEST"
test -s "$MANIFEST.sig"
trust=(--trusted-key /etc/ghaf/update/update.pub
       --uki-trusted-cert /etc/ghaf/update/db.crt
       --target intel-laptop-debug-secure-ab
       --accepted-generation-file /persist/common/ota/accepted-generation)
ota-update image validate --manifest "$MANIFEST" "${trust[@]}"
ota-update image --dry-run install --manifest "$MANIFEST" "${trust[@]}"
```

Output: successful authenticated validation and a printed plan; no slot write
has happened yet. Keep this root shell open so `$MANIFEST` and `trust` remain
available for the next command block.

Stop on any error. Confirm the dry-run writes only the inactive pair and ends
with `bootctl set-oneshot <candidate>.efi`. A `set-default` activation means the
updater lacks the [rollback fix](/ghaf/dev/architecture/ab-update#boot-health-and-rollback);
stop and deploy the fixed updater before staging a trial.

After inspecting the plan, install and confirm the permanent EFI default is
unchanged. `bootctl list` can show the one-shot candidate as the next default;
compare the persistent EFI variable itself:

```bash
DEFAULT_VAR=/sys/firmware/efi/efivars/LoaderEntryDefault-4a67b082-0a4c-41cf-b6c7-440b29bb8c4f
cp "$DEFAULT_VAR" /run/ab-default-before
ota-update image install --manifest "$MANIFEST" "${trust[@]}"
cmp /run/ab-default-before "$DEFAULT_VAR"
bootctl status --no-pager
ls /boot/EFI/Linux/
```

The install must leave a complete candidate `+3.efi`, preserve the active pair,
and return without rebooting. Inspect those outputs before issuing the reboot
as a separate action in the same root host shell:

```bash
systemctl reboot
```

The SSH session closes. Reconnect to the host, reopen a root shell, and repeat
the baseline commands (do not recreate the sentinel). If SSH reports a changed
host key, verify the laptop identity and
`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` over its identified serial
console before replacing that host's saved key. The host key can regenerate
on reboot; the network VM's key is a separate identity. After a healthy update:
running and accepted generations advance, the healthy candidate becomes the
permanent default, its counter disappears, and the persistence digest and LV
UUID remain unchanged. Repeat with a third healthy generation to prove A→B→A
reuse; two successful increasing updates are needed after initial installation.

## Automatic rollback test

Input: the healthy generation/entry and retained sentinel digest from the
previous baseline. On the build host choose a new generation and its fresh
`PUBLIC`/`SIGNED_DIR` paths as above. Replace only the config-export command in
the update recipe with:

```bash
nix run .#ghaf-secure-ab-config -- --key-dir "$GHAF_DEV_KEY_DIR" \
  --generation "$GENERATION" --output "$PUBLIC" --inject-boot-health-failure
```

Then run that recipe's remaining build and signing commands. Output: a separate
signed bundle whose UKI boots the injected failing health service. Deliver it
through the same HTTP → `net-vm` → shared host path, then validate and install.
Do not first export a healthy config at the same path, reuse a published fetch
directory, or alter the signed bundle.

Before rebooting, open a separate **build-host terminal** for capture. Obtain
`SERIAL_DEVICE` from `/dev/serial/by-id/` and match the adapter to the laptop's
configured console; it must not be another board's console. With access to that
TTY, start this capture (115200 baud), retaining the printed path:

```bash
read -r -p 'Laptop serial-console path on the build host: ' SERIAL_DEVICE
SERIAL_LOG=$(mktemp /var/tmp/ghaf-x86-rollback-serial.XXXXXX)
printf 'Serial evidence: %s\n' "$SERIAL_LOG"
stty -F "$SERIAL_DEVICE" 115200 raw -echo
cat "$SERIAL_DEVICE" | tee "$SERIAL_LOG"
```

Leave that terminal running, then issue the single reboot from the host shell.
Stop capture with Ctrl+C after the final baseline; compare the captured boot
sequence, exhausted UKI filename and accepted generation with the expected
result below. The log is an output on the build host, not on the target disk.
Do not change the default, mask boot
health or select a fallback manually during the test. Expect three failed
health checks, counter progression `+2-1`, `+1-2`, `+0-3`, then a boot into the
previous healthy generation. Its accepted generation and persistence digest
must remain unchanged. A fourth candidate attempt (`+0-4`) is a failure.

A failure before the health service can re-arm the trial, such as early verity
corruption, returns to the healthy default on the next boot. Do not require
three attempts for that case. `panic=10` provides panic reboot; hard hangs need
separate physical watchdog/reset validation. Manual recovery is a failed
automatic-rollback test even when it restores a usable system.

## Automated checks and remaining hardware cases

From this checkout on an x86 host with KVM:

```bash
nix build --no-link \
  .#checks.x86_64-linux.x86-deferred-encryption \
  .#ghaf-sign-x86-image.tests.sign \
  .#ghaf-sign-update.tests.verify-input \
  .#ghaf-sign-update.tests.reject-name-collision \
  .#ghaf-fetch-update.tests.smoke
GIVC_REV=$(jq -r '.nodes.givc.locked.rev' flake.lock)
nix build --no-link \
  "github:tiiuae/ghaf-givc/$GIVC_REV#checks.x86_64-linux.vmTests-ota-update-image"
```

The encryption test covers fresh encryption, initialized-but-incomplete
encryption, completed encryption with unfinished enrollment, and verity ordering.
The GIVC test uses real UEFI boot counting and fallback; its driver re-arms
attempts to model Ghaf's health policy. It does not replace the hardware test of
the actual health service.

| Case | Procedure and pass criterion |
| --- | --- |
| Rejection | Use disposable copies: missing/wrong signature, altered manifest/root/verity/UKI and a wrong-target signed bundle must fail `image validate`. An authentic equal/older generation can pass that command but must fail `image --dry-run install`. Do not install after either rejection. A wrong-target test needs a valid signature to isolate target policy. |
| Encryption interruption | On a disposable install, interrupt during reencryption and after encryption before enrollment completes. Reboot with the installer marker intact; setup resumes and finishes before store activation. |
| Recovery unlock | Use the credential saved from first-boot enrollment; verify it with hardware-token unlock unavailable; do not count an already-open mapping as success. |
| Secure Boot | Use the unsigned UKI from `result-x86-update` as the separate negative fixture; enable the matching firmware trust and require rejection of a separate unsigned UKI while preserving the signed fallback. Disabled Secure Boot cannot validate this case. |
| Corruption | Identify the inactive trial LV using the signed manifest hash and `ota-update image status`; corrupt only that root or verity LV on a disposable system; require reset and fallback, with the healthy pair and persist retained. |
| Power loss | Cut power during staging writes, LV renames, UKI publication, one-shot selection and health acceptance; retry the exact candidate and require recovery without modifying the active pair or persist. Disconnecting a laptop charger is not a power cut while its battery supplies power. |

On the X1 Carbon Gen11, the 2026-09-25 run verified healthy 5→7→8 updates,
slot UUID reuse, interrupted HTTP fetch/retry, and three-attempt unhealthy
generation-9 rollback to generation 8. Persistence was unchanged and all nine
VMs ran after fallback. Initial-image signing and the separate installer ISO
build passed, but this run did not repeat installation or enrollment.
Firmware Secure Boot was disabled for that run. Firmware
signature enforcement, recovery-only unlock, corruption, physical power cuts
and hard-hang reset remain separate acceptance gates. Do not generalize this
result to another laptop model or to Orin.
