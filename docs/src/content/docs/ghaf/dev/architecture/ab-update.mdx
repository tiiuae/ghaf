# Secure A/B image updates

Ghaf's secure A/B update design separates a platform-independent update
contract from storage, firmware, and deployment adapters.

The shared core owns authenticated payloads, exact-target and generation
policy, transactional system slots, and health-gated boot acceptance. Platform
adapters decide how to create the initial disk, provision encryption, install
firmware trust, and recover a particular board.

:::note[Delivery boundary]
The shared mechanisms are introduced by PR #2199. NVIDIA Jetson Orin support is
provided by PR #2200 and x86 support by PR #2201. Platform build, flash,
installation, and acceptance procedures belong in those adapter guides.
:::

## Invariants

- The active root and verity pair is immutable and is never an update target.
- An update writes only an inactive or newly staged pair.
- Root and verity artifacts, their sizes, and the UKI are bound by a signed
  manifest.
- The UKI is independently signed and embeds the same root hash and generation.
- Authentication and policy checks finish before storage mutation.
- Installation verifies the staged pair before changing boot selection.
- Boot selection is committed last, and installation never reboots the system.
- A trial has three attempts and is blessed only after the configured health
  gates pass.
- The accepted generation is monotonic. Downgrades require an explicit
  debug-only override.
- Rollback changes only the immutable system pair. Shared persistent data is
  not rolled back.

## System-slot model

The shared core uses matching LVM logical-volume names:

```text
pool/root_<version>_<hash-fragment>
pool/verity_<version>_<hash-fragment>
```

During installation, temporary names use:

```text
pool/root_staging_<hash-fragment>
pool/verity_staging_<hash-fragment>
```

The installer recovers or removes incomplete staging state before starting a
new transaction. Final names are committed only after the root and verity
images reproduce the signed dm-verity root hash.

Each platform declares fixed root and verity slot capacities. Image creation
and update installation both reject an artifact whose unpacked size exceeds
the corresponding capacity. Capacity is platform policy; it does not silently
grow with a release.

The expected encrypted platform layout is:

```text
ESP -> selected UKI
system partition -> LUKS2, when enabled -> LVM volume group pool
  -> root generation A
  -> verity generation A
  -> root generation B
  -> verity generation B
  -> persistent platform volumes
```

The exact partition table, encryption enrollment, persistent volumes, and
firmware chain are adapter responsibilities.

## Pure trust configuration

Evaluation never reads process environment variables or private key
directories. A lockable non-flake input named secure-ab-build-config provides:

- schema version;
- external public trust;
- a positive generation;
- public UEFI PK, KEK, and db certificates;
- the Ed25519 update verification key; and
- the debug-only health-failure injection switch.

External configurations contain only:

```text
config.json
PK.crt
KEK.crt
db.crt
update.pub
```

They are safe to import into the Nix store. Private keys remain outside Git and
the store. The update verifier accepts either a raw 32-byte Ed25519 public key
or its 64-character hexadecimal encoding. ghaf-dev-keygen emits the raw form.

The repository input is a keyless template. Every secure A/B image, including
debug images, requires a complete external public configuration. Missing or
inconsistent public inputs fail evaluation. There is no bundled verification
key, CI trust mode, or fallback to an unsigned image.

Generate a development trust set and export its public build configuration:

```sh
umask 077
nix run .#ghaf-dev-keygen -- --output /secure/local/ghaf-dev-keys

nix run .#ghaf-secure-ab-config -- \
  --key-dir /secure/local/ghaf-dev-keys \
  --generation 8 \
  --output ./secure-ab-generation-8
```

Use the public directory as a pure input:

```sh
nix build \
  --override-input secure-ab-build-config path:./secure-ab-generation-8 \
  .#<platform-target>
```

For reproducible release automation, a wrapper flake should lock this input and
make Ghaf's secure-ab-build-config follow it.

### Proposed CI integration

CI integration is future work; these PRs do not implement a CI trust mode or
secure A/B pipeline. A future job should supply a dedicated public configuration
through the same locked input, run the package checks, and build each platform
with bounded evaluation time. Test signing keys should remain in the runner's
secret storage and outside the flake input and Nix store.

Build and hardware jobs should be separate. Hardware jobs should select an
explicit test device and record signed update, rejection, rollback, and
interruption results before promoting that platform. Missing configuration
should fail the job; it must not substitute a different image or trust root.

## Signed manifest v2

An update bundle contains:

```text
ghaf_<version>_<hash>.manifest
ghaf_<version>_<hash>.manifest.sig
ghaf_root_<version>_<hash>.raw.zst
ghaf_verity_<version>_<hash>.raw.zst
ghaf_kernel_<version>_<hash>.efi
```

The manifest contract is:

```json
{
  "manifest_version": 2,
  "system": "aarch64-linux",
  "build-system": "x86_64-linux",
  "target": "exact-authorized-target",
  "generation": 8,
  "meta": {},
  "version": "26.08.1",
  "root_verity_hash": "<64 hexadecimal characters>",
  "root": {
    "file": "ghaf_root_<version>_<hash>.raw.zst",
    "sha256": "<64 hexadecimal characters>",
    "packed_size": 2147483648,
    "unpacked_size": 6442450944
  },
  "verity": {
    "file": "ghaf_verity_<version>_<hash>.raw.zst",
    "sha256": "<64 hexadecimal characters>",
    "packed_size": 67108864,
    "unpacked_size": 134217728
  },
  "kernel": {
    "file": "ghaf_kernel_<version>_<hash>.efi",
    "sha256": "<64 hexadecimal characters>",
    "packed_size": 67108864,
    "unpacked_size": 67108864
  }
}
```

Artifact names are safe basenames resolved relative to the manifest.
packed_size bounds transport and identifies the transferred file.
unpacked_size bounds the destination slot. system records the target platform
and build-system records the native or cross builder.

The raw 64-byte detached Ed25519 signature authenticates the exact manifest
bytes. The UEFI db key signs the UKI. Validation also extracts the UKI command
line and requires its ghaf.storehash and ghaf.generation values to match the
signed manifest.

Sign an unsigned update into a new directory:

```sh
nix run .#ghaf-sign-update -- \
  --key-dir /secure/local/ghaf-dev-keys \
  --input result-update/ghaf_<version>_<hash>.manifest \
  --output signed-update
```

The signer refuses colliding artifact names, recomputes artifact metadata,
signs the UKI, and signs the manifest last.

## Shared image-construction tools

The shared storage tools are Rust CLIs from the pinned ghafpkgs input. They
operate on regular files in the Nix sandbox:

- ghaf-initialize-verity-lvm creates deterministic LVM metadata, fixed logical
  volumes, and optional inactive, swap, and persistent volumes.
- ghaf-wrap-luks-image converts a sparse plaintext image into a sparse LUKS2
  image using userspace crypto.

The LVM package is built with activation and kernel ioctls disabled. The CLI
has no block-device backend. Payload writes are capped at the logical-volume
capacity and must reach end-of-stream at that boundary. The LUKS wrapper does
not open a mapper.

Neither tool needs root, sudo, a VM, a loop device, a mount, or device mapper.
Adapter code supplies partitioning and key policy without duplicating these
mechanisms.

The Rust library owns bounded file writes, subprocess handling, and checked
LUKS publication. The offline LVM2 and cryptsetup patches and their integration
tests live alongside it in ghafpkgs. Ghaf re-exports the existing command names
and supplies configuration and platform policy; it does not carry another
implementation. LUKS construction preserves the original until successful
validation and atomic replacement. LVM construction remains in-place in a
disposable, initially zero-filled image.

LUKS wrapping encrypts all bytes in filesystem-reported data extents, including
written zeroes. Only source holes are skipped; adapters must reserve those for
unused space. Sparse encrypted holes do not decrypt to guaranteed zeroes.

## Delivery and installation

Network retrieval belongs to the network-owning VM. Trusted validation and
storage mutation belong to the Ghaf host:

```text
build and sign
  -> network VM fetch
  -> shared persistent download area
  -> host validation and install
  -> boot-counted trial
  -> health acceptance or rollback
```

ghaf-fetch-update is a debug-only static-HTTP helper. It applies fixed metadata
limits, per-kind artifact caps, manifest-declared packed-size limits, and exact
final-size checks before publishing a fetched bundle. Production delivery
should use the authenticated OCI registry support in ota-update. Transport
success never authorizes installation.

The installer transaction is:

1. Acquire the update lock.
2. Verify the detached manifest signature.
3. Validate schema, target, generation, sizes, hashes, and UKI binding.
4. Discover the active and inactive slots.
5. Snapshot and recheck the source UKI.
6. Recover stale staging state.
7. Create staging LVs and supervise decompression and writes.
8. Verify the staged dm-verity root hash.
9. Commit final LV names.
10. Atomically install the three-attempt UKI.
11. Set the candidate-specific boot default.

The lock is acquired before discovery. A private UKI snapshot closes the race
with a network-VM-writable source directory. Root and verity writes are accepted
only when the result reproduces the signed root hash.

ota-update image validate and ota-update image --dry-run install perform
non-mutating validation and planning. ota-update image install returns a
reboot-required result but never reboots automatically.

## Boot health and rollback

Trial UKIs use systemd-boot's three-attempt suffix:

```text
ghaf-<version>-<hash>+3.efi
```

The trial default is a candidate-specific glob, which continues to select the
renamed counted entry while avoiding unrelated generations. A healthy trial is
promoted to its exact UKI name.

ghaf-boot-health.service verifies:

- the configured encryption and dm-verity mappings;
- the immutable store and persistent mounts;
- the configured core MicroVM services; and
- a valid kernel generation.

For a healthy new generation it promotes the current entry, atomically persists
the accepted generation, and blesses the counted trial last. If a trial is
unhealthy, the service re-arms it while attempts remain and requests a reboot.
After exhaustion, systemd-boot selects the prior blessed entry.

The current MicroVM gate proves VMM service activity, not guest-agent
readiness. A GIVC liveness gate is required before treating this as complete
application-health acceptance.

## Adapter responsibilities

| Shared core | NVIDIA adapter | x86 adapter |
| --- | --- | --- |
| Manifest and trust policy | Jetson APP/QSPI layout | GPT and ESP layout |
| Update signing and validation | OP-TEE DUK and recovery enrollment | TPM/FIDO2 and recovery enrollment |
| Transactional LVM slots | NVIDIA Secure Boot and flash flow | UEFI Secure Boot and installer flow |
| Boot attempts and health policy | NX/AGX first-boot provisioning | Type-2 UKI and systemd-boot policy |
| Regular-file LVM/LUKS tools | Board-specific watchdog acceptance | Laptop-specific hardware acceptance |

Hardware evidence is platform-specific. NX results do not accept AGX behavior,
and one x86 laptop does not establish support for every laptop target.

## Security boundaries

- Development keys are not production key management.
- Private signing keys never enter the Nix store.
- Persistent data is not rolled back with the immutable system.
- Partition and ESP confidentiality is not provided by this design.
- Initial installation and trust enrollment remain platform-specific,
  potentially destructive operations.
- Build success is not hardware acceptance.
- Release readiness requires signed A-to-B-to-A reuse, wrong-target and
  downgrade rejection, corruption rollback, recovery-key testing, power-loss
  testing at every transaction phase, and demonstrated automatic health
  rollback on every promoted hardware target.
